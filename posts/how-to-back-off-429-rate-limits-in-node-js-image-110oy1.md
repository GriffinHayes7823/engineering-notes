# How to Back Off 429 Rate Limits in Node.js Image Uploads (Object Storage Queue)

Short answer: put AI image generation and object storage upload in separate queue steps, save the generated bytes between them, and retry a `429` upload with backoff against a job-derived object key. For authenticated customer reports, keep every object private and issue a short-lived signed URL at delivery time.

That choice favors access control over the absolute shortest delivery path. A direct public URL would remove work, but it is the wrong primitive for customer-specific reports, and this storage surface does not provide public or `public-read` objects anyway. The useful question is not whether a retry exists. It is whether every retry preserves the identity of the generated artifact and its authorized owner.

## Reliability: define failure recovery before choosing storage

Reliability starts with a narrow recovery contract. Before selecting storage, write down what a replay is allowed to change. In this pipeline it may change the attempt number and the next eligible time. It may not change the generated bytes, customer account, report job, or final object key. That contract turns a vague promise to “retry later” into a condition an operator can test.

The failed/simple approach violates the contract because generation and upload share one queue acknowledgement. Any upload rejection re-enters generation. The chosen design acknowledges generation after the bytes have been saved, then gives upload its own retry record. Recovery can therefore move forward from `bytes_saved`; it never jumps backward to `requested`.

This matters even before cost enters the discussion. Two generations for one report create ambiguous provenance: which byte sequence did the customer approve, and which checksum belongs in the audit record? A reliable replay has one answer.

## Migration: which private storage boundary can the team keep?

Migration risk changes the storage decision. The first choice is direct vendor integration versus an aggregation layer, not a price spreadsheet. Infrai is a credible fit for a solo team already consuming several backend capabilities because storage sits behind the same REST conventions, key, wallet, and bill; no storage-specific SDK is required. Its public discovery also describes request and response schemas. The catch is that this convenience comes with real storage boundaries: no public objects, object versioning, object lock, automatic cross-region replication, or cross-cloud bulk migration; lifecycle expiry starts at one day, and metadata cannot be searched server-side.

Those limits make private generated reports a reasonable fit, but not every storage workload.

| Option | What the available coverage establishes | Decision for this report pipeline |
| --- | --- | --- |
| Infrai aggregation | Routes storage through R2, S3, OSS, or COS under one REST API and one account relationship | Consider it when fewer keys, SDKs, and invoices matter more than provider-specific storage controls |
| Direct Amazon S3 | S3 is one of the covered storage vendors | Stick with a direct integration when the required provider-specific controls exceed the aggregate surface |
| Direct Cloudflare R2 | R2 is one of the covered storage vendors | Prefer direct access when R2-specific configuration is part of the design |
| Direct Alibaba Cloud OSS | OSS is one of the covered storage vendors | Prefer direct access when the application depends on OSS-specific behavior |
| Direct Tencent Cloud COS | COS is one of the covered storage vendors | Prefer direct access when COS-specific behavior is a requirement |
| Google Cloud Storage or Backblaze B2 | Neither GCS nor B2 is in this vendor coverage | Choose the provider directly, or another abstraction, when either is mandatory |

This is also not suitable for static website hosting, a permanent image host, or any flow that needs a public asset URL: `public_url` remains null and there is no public-read ACL. Browser-direct uploads are another poor match when the application must self-configure CORS, because there is no independent CORS setup route available to the caller. Financial records that require WORM retention should use an external solution with object lock. These are product-shape decisions, not defects a retry loop can hide.

Access is the upside here. An application can authorize `account_42` against its own report row, obtain a time-limited presigned URL for the private key, and return that URL only to the customer who owns the report. The download response may use `Content-Disposition` to suggest a filename, but authentication and authorization must happen before URL issuance. Don't turn the object key into an authorization policy.

## Governance: bind one generated image to one customer report

Governance needs an explicit owner for every transition. Treat generation and upload as two state transitions: `requested -> bytes_saved -> object_stored`. The generation worker writes the finished bytes to durable job storage and records their checksum. Only then does it enqueue the upload worker. If object storage returns HTTP `429`, the second worker reads those same bytes and tries again; it does not ask the image model to reproduce them.

The invariant is `one report job -> one saved byte sequence -> one private object key`. A single combined worker often looks tidy because one function generates an image and immediately uploads it. Then the final network call is rate-limited, the queue retries the entire function, and an already completed generation runs twice. The customer may receive the same visual result, a slightly different result, or two candidate artifacts, while the operator has a muddy job history. Separating the steps makes the retry boundary match the failed operation and leaves a record that can be audited.

Keep the object key deterministic as well. For a report job named `report_7f31`, a key such as `reports/account_42/report_7f31/hero.png` is better than a random UUID produced inside every attempt. All attempts converge on one destination. Since there is no `If-Match` conditional write, however, a deterministic key is not a lock: the database or queue must ensure that two workers cannot commit competing bytes to that key. I would use a unique job claim in the database and let only the claim holder upload.

Small boundary. Big consequence.

## How should a Node.js queue decide 429 retry backoff after image generation?

Retry only the upload stage, cap the number of attempts, add jitter, and honor `Retry-After` when it is present. A tight loop converts one rate limit into a larger burst. A fixed delay makes many workers wake together. Exponential backoff with jitter spreads them out, while the server-provided delay remains the best instruction when available.

The queue payload should contain a job ID, account ID, saved-byte location, checksum, and attempt count. It should not contain a public URL or a fresh random object key. On success, store the private object key in the report record; the authenticated download handler can later request a presigned URL and redirect the authorized customer. Do not forward the storage API authorization header to that returned URL.

There are two non-retry outcomes worth separating. An ordinary non-`429` client response should surface its body and stop automatic retries until the input or account state changes. A trial environment also cannot fund persistent writes, so a `trial_restricted` upload will not become valid after sleeping for another few seconds. That is an account constraint, not queue congestion.

I'm not sure what retry ceiling fits every image provider or report SLA, because the available facts do not establish one. Measure the actual queue delay and customer deadline, then set the cap. The sample below uses five attempts as an explicit local policy, not a universal vendor limit.

## Implementation: a focused Node.js object storage upload worker

This worker assumes the generation step has already atomically saved bytes under `SAVED_IMAGE_PATH`. It calls one verified route, uses a key derived from immutable job data, and makes every HTTP method explicit. The example requires Node.js 20 or newer and a TypeScript runner such as `tsx`.

```ts
import { readFile } from "node:fs/promises";

const required = (name: string): string => {
  const value = process.env[name];
  if (!value) throw new Error(`Missing ${name}`);
  return value;
};

const apiBase = required("STORAGE_API_BASE_URL").replace(/\/$/, "");
const apiKey = required("INFRAI_API_KEY");
const bucket = required("REPORT_BUCKET");
const accountId = required("ACCOUNT_ID");
const jobId = required("REPORT_JOB_ID");
const savedImagePath = required("SAVED_IMAGE_PATH");
const objectKey = `reports/${accountId}/${jobId}/hero.png`;
const objectPutRoute = "/v1/storage/object/put/{bucket}/{key}";
const maxAttempts = 5;

const sleep = (milliseconds: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, milliseconds));

const retryDelayMs = (response: Response, attempt: number): number => {
  const retryAfter = response.headers.get("retry-after");
  if (retryAfter) {
    const seconds = Number(retryAfter);
    if (Number.isFinite(seconds)) return Math.max(0, seconds * 1_000);

    const dateDelay = Date.parse(retryAfter) - Date.now();
    if (Number.isFinite(dateDelay)) return Math.max(0, dateDelay);
  }

  const exponential = Math.min(30_000, 500 * 2 ** (attempt - 1));
  return exponential + Math.floor(Math.random() * 250);
};

const uploadSavedImage = async (): Promise<void> => {
  const bytes = await readFile(savedImagePath);
  const path = objectPutRoute
    .replace("{bucket}", encodeURIComponent(bucket))
    .replace(
      "{key}",
      objectKey.split("/").map(encodeURIComponent).join("/"),
    );

  for (let attempt = 1; attempt <= maxAttempts; attempt += 1) {
    const response = await fetch(`${apiBase}${path}`, {
      method: "PUT",
      headers: {
        Authorization: `Bearer ${apiKey}`,
        "Content-Type": "image/png",
      },
      body: bytes,
    });

    if (response.ok) {
      process.stdout.write(`${JSON.stringify({ jobId, objectKey })}\n`);
      return;
    }

    const detail = await response.text();
    if (response.status !== 429 || attempt === maxAttempts) {
      throw new Error(`Upload rejected (${response.status}): ${detail}`);
    }

    await sleep(retryDelayMs(response, attempt));
  }
};

await uploadSavedImage();
```

Run it with queue-supplied values rather than literals in source control:

```bash
INFRAI_API_KEY="${INFRAI_API_KEY}" \
STORAGE_API_BASE_URL="${STORAGE_API_BASE_URL}" \
REPORT_BUCKET="customer-reports" \
ACCOUNT_ID="account_42" \
REPORT_JOB_ID="report_7f31" \
SAVED_IMAGE_PATH="/var/lib/report-jobs/report_7f31/hero.png" \
npx tsx upload-report-image.ts
```

The queue still needs a claim around the upload state. For example, update `bytes_saved` to `uploading` only when the row is still `bytes_saved`, then acknowledge the queue message only after the object key has been recorded as `object_stored`. That compare-and-set belongs in the database because the object API itself has no conditional `If-Match` write. If a worker loses its claim, it should stop before sending bytes. This is the part a code snippet cannot safely guess for a reader's database schema.

## Release decision: can a recovery drill prove this queue design?

Track generation completions, saved-byte age, upload attempts, `429` counts, time spent honoring `Retry-After`, and the end-to-end age of each report. Record the job ID and object key together so an operator can distinguish a delayed upload from an unnecessary regeneration. Also watch bytes that were saved but never reached `object_stored`; they need an explicit retention policy, especially because lifecycle expiry cannot be shorter than one day and multipart fragments have no automatic cleanup rule.

Then test the awkward sequence on purpose: generation completes, bytes are saved, the first upload receives `429`, and a later attempt writes the same key. Verify that generation ran once, only the database claim holder uploaded, and the customer could access the final private object through a newly issued signed URL. No drama. Just evidence.

For a solo team, my decision rule is plain: use the aggregate API when private report delivery and operational consolidation are the priority; use S3, R2, OSS, or COS directly when a provider-specific control is a requirement; and choose another path when GCS, B2, public hosting, browser-managed CORS, WORM retention, or automatic cross-region replication is non-negotiable.
